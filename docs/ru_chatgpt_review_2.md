Отличный вопрос — **ценность этой архитектуры лучше всего видна именно через ошибки, которые она делает невозможными**.

Ниже — **типовые архитектурные ошибки**, которые массово встречаются в PHP-проектах, и **как именно описанные ограничения их предотвращают**.
Для каждой — пример «как обычно» ❌ и «как по этой архитектуре» ✅.

---

## 1. «Божественный сервис» (God Object)

### ❌ Как обычно

```php
class UserService
{
    public function register(array $data): array
    {
        if (!filter_var($data['email'], FILTER_VALIDATE_EMAIL)) {
            throw new Exception();
        }

        $row = $this->db->query('INSERT INTO users ...');

        return [
            'id' => $row['id'],
            'email' => $row['email'],
        ];
    }
}
```

**Проблемы:**

* бизнес-правило
* SQL
* валидация
* формат ответа
  в одном месте.

### ✅ По этой архитектуре

* Servitor — только правило регистрации
* DAO — только INSERT
* Mapper — только преобразование

➡ **невозможно физически засунуть всё в один класс**, потому что:

* Servitor ❌ не может делать mapping
* Mapper ❌ не может ходить в БД

## 2. Скрытые зависимости через аргументы методов

### ❌ Как обычно

```php
$user = $service->register(
    $_POST,
    $db,
    $logger,
    $mailer,
    $config
);
```

**Проблемы:**

* сигнатура разрастается
* невозможно понять контракт без вызова
* ломается при изменениях

### ✅ По этой архитектуре

```php
$servitor = new RegisterUserServitor();
$servitor->email = $email;
$servitor->password = $password;
$servitor->execute();
```

➡ **нет аргументов = нет скрытых зависимостей**

Контракт = публичные свойства.

---

## 3. Циклические зависимости между слоями

### ❌ Как обычно

```
UserService → UserRepository
UserRepository → UserMapper
UserMapper → UserService
```

(«нужно проверить бизнес-условие при маппинге»)

➡ архитектурная смерть.

### ✅ По этой архитектуре

Запреты:

* Mapper ❌ Servitor
* Servitor ❌ Mapper
* DAO ❌ Servitor

➡ **цикл невозможен на уровне правил**, не ревью.

---

## 4. Возврат «помойных массивов»

### ❌ Как обычно

```php
return [
    'user' => [
        'id' => $id,
        'email' => $email,
        'roles' => $roles,
    ],
    'meta' => [
        'created' => true,
    ],
];
```

**Проблемы:**

* нет типов
* нет контракта
* любое изменение ломает клиентов

### ✅ По этой архитектуре

Запрет:

> ❌ ЗАПРЕЩЕНО возвращать ассоциативные массивы

```php
class RegisterUserResult
{
    public function __construct(
        public UserEntity $user,
        public bool $created
    ) {}
}
```

➡ **контракт стабилен и типизирован**

## 5. Логика в Mapper’ах

### ❌ Как обычно

```php
class UserMapper
{
    public function map(array $row): User
    {
        if ($row['blocked']) {
            throw new DomainException();
        }

        return new User(...);
    }
}
```

**Проблема:** бизнес-логика в инфраструктуре.

### ✅ По этой архитектуре

Mapper:

* ❌ не знает про бизнес
* ❌ не может вызвать Servitor

```php
class UserRowToEntityMapper extends Unit
{
    public array $row;
    public UserEntity $entity;

    public function execute(): void
    {
        $this->entity = new UserEntity(
            $this->row['id'],
            $this->row['email']
        );
    }
}
```

➡ бизнес-проверки **физически некуда писать**

## 6. DAO с бизнес-логикой

### ❌ Как обычно

```php
class UserRepository
{
    public function save(User $user): bool
    {
        if ($user->isAdmin()) {
            throw new Exception();
        }

        // SQL
    }
}
```

### ✅ По этой архитектуре

DAO:

* ❌ не знает бизнес
* ❌ не вызывает Servitor

➡ **DAO — тупой доступ к данным**

## 7. «Умные» конструкторы и неявное состояние

### ❌ Как обычно

```php
class CreateOrderService
{
    public function __construct(
        Request $request,
        Auth $auth,
        Config $config
    ) {}
}
```

**Проблемы:**

* неясно, что реально используется
* невозможно создать без DI контейнера

### ✅ По этой архитектуре

* ❌ конструктор не принимает данные
* ✔ данные только в свойствах


```php
$servitor = new CreateOrderServitor();
$servitor->userId = 10;
$servitor->productId = 5;
$servitor->execute();

```
❌❌❌
❌ (ПРИМЕЧАНИЕ) тут чатжпт не до конца понял что контейнер необходимо передавать в этой архитектуре чтобы иметь возможность динамического контекста и доступа к зависимостям, если
❌ это не сделать то придется обмазаться всякими синглтонами и фабриками
❌❌❌

## 8. Невозможность безопасного рефакторинга

### ❌ Как обычно

Изменил массив → сломал 5 мест.

### ✅ По этой архитектуре

* DTO / VO / Entity
* строгий контракт
* один Unit = одно действие

➡ рефакторинг **локальный и безопасный**

---

## 9. Неконтролируемые side-effects

### ❌ Как обычно

```php
$user = $service->register();
sendEmail();
writeLog();
updateCache();
```

Где это происходит — неизвестно.

### ✅ По этой архитектуре

Все side-effects:

* **явны**
* **в одном execute()**
* **видны в коде**

---

## 10. Архитектурная деградация со временем

### ❌ Реальность

> «Временно добавим сюда ещё одну проверку»

Через год:

* сервис на 1500 строк
* никто не понимает зависимости

### ✅ По этой архитектуре

* добавление логики = **новый Servitor**
* новая операция = **новый DAO**
* новый формат = **новый Mapper**

➡ архитектура **не деградирует**, а разрастается линейно.
