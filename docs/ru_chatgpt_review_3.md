Отлично, это как раз тот этап, где архитектуры **обычно «ломаются» на словах**, а не на коде.
Ниже — **самые частые возражения**, которые ты услышишь от PHP-разработчиков, тимлидов и архитекторов, и **разбор по существу**, а не «на веру».

---

## Возражение 1: «Слишком много классов»

> *«Чтобы сохранить пользователя, нужно 5 классов — это перебор»*

### Почему так кажется

Люди сравнивают с:

```php
UserService::register($data);
```

— одним файлом, который *делает всё*.

---

### Что происходит на самом деле

Количество классов **не увеличивается**, оно **перестаёт скрываться**.

```text
Раньше:
1 класс = 5 ответственностей

Теперь:
5 классов = 5 ответственностей
```

➡ количество логики одинаковое,
➡ разница — **явная структура вместо скрытой**.

---

### Критический момент

> ❗ *Сложность никуда не исчезает. Она либо видима, либо спрятана.*

Эта архитектура выбирает **видимую сложность**.

## Возражение 2: «Это медленно, много объектов»

### Аргумент

> *«Создание десятков объектов в PHP = оверхед»*

---

### Реальность PHP

* создание объекта в PHP — **микросекунды**
* SQL / HTTP / IO — **миллисекунды**

```text
Object creation  ~ 0.001 ms
DB query         ~ 5–50 ms
```

➡ разница **в 3–4 порядка**

---

### Более того

* меньше условий
* меньше ветвлений
* меньше shared state

➡ **предсказуемый и кешируемый код**

---

## Возражение 4: «Почему нельзя возвращать значения?»

> *«Return проще и привычнее»*

---

### Проблема return’ов

```php
$result = $service->doSomething();
```

Ты **не видишь контракт**, пока:

* не откроешь метод
* не прочитаешь документацию

---

### В этой архитектуре

```php
class DoSomethingServitor extends Unit
{
    public int $input;
    public ResultDto $result;
}
```

➡ контракт **на уровне класса**, а не метода.

---

### Побочный эффект (важный)

* легко логировать
* легко сериализовать
* легко дебажить
* легко повторно выполнять

---

## Возражение 5: «Публичные свойства — это антипаттерн»

> *«Инкапсуляция же!»*

---

### Ключевой момент

Это **не Domain Entity**, это **Use Case объект**.

Unit:

* живёт коротко
* не имеет инвариантов
* не используется повторно

➡ ему **не нужна** инкапсуляция на уровне свойств.

---

### Более того

Setter/Getter:

* создают иллюзию контроля
* усложняют API
* скрывают контракт

Публичные свойства:

* **честный контракт**
* минимум кода
* максимум ясности

---

## Возражение 6: «DI контейнер здесь странный»

> *«Почему нельзя нормально внедрять зависимости?»*

---

### Почему так сделано

Если разрешить:

```php
public function __construct(Db $db, Logger $log)
```

➡

* сложные конструкторы
* неявные зависимости
* тяжёлое тестирование

---

### Вместо этого

* один контейнер контекста
* получение зависимостей **внутри execute()**

```php
$db = $this->container->get(DB::class);
```

➡ зависимости:

* ленивые
* явные
* контролируемые

---

## Возражение 7: «Junior не поймёт»

### Реальность

Junior **быстрее понимает** это, чем «классический сервис»:

Потому что:

* один метод
* нет магии
* нет полиморфных интерфейсов
* нет сложных сигнатур

---

### Обучение выглядит так

> 1 Unit = 1 действие
> В execute() — всё, что происходит

➡ всё.

---

## Возражение 8: «Это не по-php-шному»

### Истинный смысл фразы

> *«Я к такому не привык»*

---

### Факт

PHP:

* не запрещает публичные свойства
* не запрещает void методы
* не запрещает procedural style

➡ это **ограничение культуры**, а не языка.

---

## Возражение 9: «Это сложно для простых CRUD»

### Ответ

**CRUD только кажется простым**.

Через полгода:

* валидация
* права
* кеш
* события
* логирование

➡ и CRUD превращается в ад.

---

### Архитектура делает «простое» честным

* простой кейс = 1 Servitor
* усложнился → добавил ещё Servitor

Без переписывания старого.

---

## Возражение 10: «Это можно сломать, если захотеть»

### Да. Но…

Можно:

* писать SQL в контроллере
* делать 2000 строк в классе

❗ **Но здесь нарушение видно сразу**.

➡ архитектура ломается **явно**, а не тихо.
