Это очень правильный следующий вопрос.
**Сильная архитектура ≠ универсальная архитектура.**
Ниже — **честный разбор, где эта модель НЕ подходит или даёт отрицательную ценность**, без оправданий и фанатизма.

---

## 1. Одноразовые скрипты и throw-away код ❌

### Примеры

* CLI-скрипт для миграции данных «на один раз»
* cron, который проживёт неделю
* quick-fix под дедлайн

### Почему не подходит

* overhead на структуру > ценность
* архитектурные гарантии не успевают окупиться

```php
// тут архитектура — вред
foreach ($rows as $row) {
    $db->insert($row);
}
```

➡ **процедурный код честнее и дешевле**

---

## 2. Очень маленькие проекты (1–2 файла) ❌

### Пример

* лендинг
* простой webhook
* REST endpoint с 1 SQL запросом

### Почему

* нет роста
* нет команды
* нет сопровождения

Архитектура — это **инвестиция**, а не необходимость.

---

## 3. Domain-rich DDD с сильными инвариантами ❌ / ⚠️

### Проблема

Эта архитектура:

* не держит состояние
* не защищает инварианты
* не живёт долго

```php
$order->addItem();
$order->applyDiscount();
$order->confirm();
```

➡ здесь **Entity должна быть умной**, а Unit — тупым.

### Вывод

* ❌ плохо для rich domain model
* ✔ хорошо для **anemic domain + use cases**

---

## 4. Системы с долгоживущим состоянием ❌

### Примеры

* игровые серверы
* real-time симуляции
* сложные workflow engines

### Почему

Unit:

* создаётся → выполняется → умирает
* не хранит состояние между вызовами

➡ тут нужен:

* state machine
* actor model
* event sourcing

---

## 5. Высоконагруженные hot-path участки ⚠️

### Пример

* обработка миллионов сообщений в секунду
* tight loops
* realtime scoring

### Проблема

* object churn
* memory pressure
* GC

➡ в hot-path:

* процедурный код
* плоские функции
* data-oriented подход

**Но:** это 1–5% системы.

---

## 6. Framework-centric архитектуры (Laravel / Symfony) ⚠️

### Конфликт

| Фреймворк | Конфликт                            |
| --------- | ----------------------------------- |
| Laravel   | Services, Repositories, Facades     |
| Symfony   | Autowiring, Controllers as services |

Фреймворки:

* продвигают DI
* навязывают lifecycle
* любят return значения

➡ архитектура **идёт поперёк** idiomatic usage.

### Решение

Использовать:

* Units **внутри** контроллеров
* не пытаться заменить весь фреймворк

---

## 7. Команды без архитектурной дисциплины ❌

### Парадокс

Архитектура строгая —
но требует **согласия команды**.

Если:

* нет code review
* нет архитектурного владельца
* «каждый пишет как хочет»

➡ будет:

* полураспад
* гибрид
* хаос

---

## 8. Где важнее скорость фич, чем качество ❌

### Реальность стартапов

* pivot каждую неделю
* код выкидывается
* нет времени на рефакторинг

➡ архитектура не окупится.

---

## 9. UI-heavy / frontend-logic systems ❌

### Примеры

* SPA с бизнес-логикой на фронте
* backend = thin BFF

➡ Units становятся прокси без ценности.

---

## 10. Когда нужен polymorphism > orchestration ⚠️

### Пример

```php
$payment->pay();
```

vs

```php
$servitor->execute();
```

Если система:

* строится на стратегиях
* плагинах
* runtime-подмене поведения

➡ эта архитектура **слишком процедурная**.
